# 数据导入与标准化

## 两类报表

系统先区分粒度，再谈字段。

- **汇总报表**：一个平台、一个币种、一天一行。现在的平台日报就是这种。
- **明细报表**：一笔充值、一个用户或一个游戏一行。现在还没有。明细不能和汇总加在同一张事实表里。

识别顺序：看表头和行结构，不靠文件名下最终结论。文件名只作为币种和平台的提示。提示和内容冲突时，以你在预览里确认的选择为准。

「总计」「合计」以及日期不是 YYYY-MM-DD 的行，不进入事实表。

## 导入步骤

1. 你选择文件，或从本机收件夹挑选。
2. 系统读出表头和前几行，判断更像汇总还是明细。判断不了就标成「未识别」，请你选。
3. 系统按该平台、该报表类型已保存的模板提出字段映射。没有模板时，你手动指定哪一列是日期、平台、币种和指标。
4. 预览显示：将写入多少天，将覆盖哪些天，哪些行被丢掉，哪些等式对不上。
5. 你确认后才写入。写入同时保存原始文件副本、原始表和标准化结果。
6. 覆盖不是删除历史。旧批次仍可查看，正式指标指向你确认的最新批次。

## 字段映射

模板按「平台 + 报表类型」保存。Afun-MX 和 Betroia 的当前日报表头相同，第一版可以共用一个模板，仍分开存储数据。

映射只把源列指向标准字段。不在映射里做除法或猜测。例如不能把「充值人数 − 新充人数」映射成老用户人数。

未知列保留在原始表里，不丢。以后新增指标时还能用旧文件重放。

## 标准化之后的结构

第一张正式事实表是「平台日」。一行代表一个平台、一个市场、一个币种、一个业务日期、一个导入批次。

列只放源文件里直接有的度量，外加批次号。不在入库时写入推算列。推算放在指标层，并且必须能回到这些列。

平台日至少包括：日期、平台、市场、币种、活跃人数、注册人数、充值人数、充值笔数、充值金额、首充人数、首充金额、新充人数、新充金额、老用户充值人数、提现金额、提现人数、KOL工资、充提差、投注金额、返奖金额、公司输赢。

比率列，例如有效新增率、付费率、复登率，先原样收进原始表。第一版不把它们登记成可归因指标，因为它们是文件里的比率，分母不一定在同行能复原。

第二张事实表「维度日」先建空结构，字段包括维度类型、维度名、度量和批次。没有游戏或通道文件时，这张表是空的。总览不允许从平台日拆出维度日。

## 校验

每次导入至少检查：

- 同一批次里，平台、日期、币种重复。
- 人数为负。
- 日期超出文件声称的范围，或不是合法日期。
- 已核对等式是否仍然成立。不成立则该日标记为「等式未通过」，指标页仍显示原始列，但归因层不使用这条等式。
- 比索和美金的人数不一致。不一致时两份都保留，并在币种切换时提示人数源不一致。不自动挑一个。

金额为 0 是合法值。空白不是 0。

## 追加和修正

追加是新的日期。修正是你明确覆盖已有日期。两种都产生新批次。

不能在后台静默用新文件改旧结论。分析笔记如果引用了被覆盖的批次，笔记上显示「源批次已不是当前正式版本」。

## 币种和时区

币种是数据的一部分，不是显示时临时涂上去的。比索文件和美金文件各写各的平台日。

显示美金时读美金行。没有美金金额、但有已通过稳定性检查的汇率时，才换算金额，并在问号里说明用了汇率。人数永远读原值。

业务日期按文件里的日期，不按上传时刻的时区改写。文件里的日期视为墨西哥自然日。自然日结束后再过 3 小时，那一天才可导入。这套窗口继续用于新产品。如果以后有别的市场，日期要带市场上的时区规则，不能沿用墨西哥。

## 以后的接口和数据库

导入层和存储层分开。以后 API 或数据库同步只是另一种「批次来源」，仍然要经过预览、映射和校验。第一版不实现这条通路，只在批次上来源类型留出 file、api、database 三个值，现在只用 file。
