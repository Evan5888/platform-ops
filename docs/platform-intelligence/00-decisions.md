# 已经确定、设计建议、必须等报表

判断分三类。

- **已确定**：你已经定过方向，或者现有日报里已经核对过的事实。
- **设计建议**：我为了把系统做出来提出的做法。你确认之前，不按这个写代码。
- **等待报表**：现有文件里没有这一列或这一种明细。不能编一个数，也不能先做这个分析。

## 已确定

产品要回答五件事：现在经营怎么样，哪些指标变了，变化来自哪些能拆开的部分，背后可能是什么问题，下一步该查什么或做什么。结论必须来自文件里的数。相关不等于原因。

第一版给你一个人用。以后要能加平台、国家、权限、共享报告和长期记录。第一版不做登录和多人权限，但数据要按平台分开存。

第一阶段的数据是业务后台导出的 Excel 和 CSV，不接生产数据库，不接外部接口。

现在已经有的报表，是 Afun-MX 和 Betroia 的平台日报，各有墨西哥比索和美金两份。每天一行，从 2026-10-01 到 2026-11-15，共 46 天。最后一行「总计」不能拿来算指标、画图或算汇率。这是汇总报表，不是逐笔交易，也不是游戏或渠道明细。

人数不按汇率换算。金额优先用该币种的原文件。每个平台有自己的汇率，含义是 1 美金等于多少比索。Afun-MX 的稳定中位数是 18.67，Betroia 是 17.4245。画面上汇率只显示两位小数。比值如果不稳定，就不压成一个数。

用这两份比索日报逐日核对过，下面几条在 46 天里都成立：

- 充值人数 = 首充人数 + 老用户充值人数。
- 全量 Arppu = 充值金额 / 充值人数（允许报表自己的四舍五入）。
- 首充 Arppu = 首充金额 / 首充人数（同样允许四舍五入）。
- 公司输赢 = 投注金额 − 返奖金额。这批数据里彩金投注和彩金返奖是 0，所以彩金不为 0 时这条是否还成立，要再核对。
- 充提差 = 充值金额 − 提现金额 + KOL工资。Afun-MX 有 3 天 KOL工资不是 0，加上之后才对得上。

下面几条已经核对过，不能当成事实：

- 充值人数减新充人数，不等于老用户充值人数。46 天都对不上。
- 日报里没有「老用户充值金额」。老用户金额不能推导。
- 新充人数每天都小于首充人数。新充不是首充的另一种叫法，也不是老用户的补集。

界面语言是中文。使用以桌面为主。平台是第一层选择，选中之后再看这个平台的总览、用户和游戏。

活跃人数可以叫 DAU，公司输赢可以叫 GGR。页面同时保留日报原列名，写成「活跃人数（DAU）」和「公司输赢（GGR）」。过去七天的活跃人数仍是每日人数相加，不是七天去重人数。公司输赢在本批彩金为 0 时等于投注金额减返奖金额；彩金不为 0 的新数据要再核对后，才能继续把这条当成 GGR 的公式。

KOL工资是请的网红达人，通过平台账户发给他们去提现。充提差的算式不变：充值金额 − 提现金额 + KOL工资。

导入日期沿用现有看板：文件里的日期是墨西哥自然日，自然日结束后再过 3 小时，那一天才可导入。

新系统的服务用 FastAPI，分析库用 DuckDB。pandas 和 Parquet 仍按技术架构作为读表和存档的配套。第一版数据存在本机。PostgreSQL、登录和自动同步仍留到后期。

## 待确认的界面方案

2026-11-17 你看过当前页面后，认为它仍像运营数据展示页，而不是经营诊断系统。第一阶段原型和线上运营看板都先留着，不删。

新的导航、总览、波动归因、交互和视觉规范写在 `docs/platform-intelligence/redesign/`。你确认那组文档之前，不按它改前端。指标公式、别名、KOL工资、导入窗口和 FastAPI / DuckDB 不因这次重设计而改变。

## 设计建议

新产品不要直接改掉现在的运营看板。看板继续单独运行。Platform Intelligence 作为旁边的一套新程序来做。你确认阶段 1 之前，不动已经上线的页面。

网页继续用 React、TypeScript、Tailwind CSS 和 ECharts。第一阶段界面是手写组件，还没有改用 shadcn/ui。FastAPI 和 DuckDB 已经确认，见上面。PostgreSQL、登录和自动同步留到后期。利弊写在技术架构文档里。

第一版指标只采用上面核对过的字段和等式。文件里已有、但还没逐日对账的比率，只展示原值，不重新解释成另一种指标。

波动分析先做「这一天对前一天」和「这一天对过去七个有数据的日子」。七天合计只加文件里存在的日期，缺的日期不加 0。人数类的「过去七天」是每日人数相加，不是七天里的去重人数。

归因分成四层，画面上必须能分清：已核对的变化、能用等式算出的驱动、可能的业务假设、证据不够所以不下结论。

AI 助手放到阶段 6。它只能转述已经算好的结果。不能自己编数字，也不能把公司报表发给未授权的外部服务。

演示数据如果用来看布局，每一页都要标成「演示」。演示数字不能和真实日报出现在同一张没有标记的图里。

## 等待报表

这些需求现在不能做实，因为现有日报没有对应明细：

- 渠道、代理、推广消耗。
- 支付通道、充值发起笔数、充值成功率。
- 游戏、厂商、游戏类别的投注、派奖和输赢拆分。
- 单个用户的留存、分层和生命周期价值。
- 新访问 IP、登录记录、CRM、播报和监控。

没有这些文件之前，对应的页面可以留空，并写明缺哪一种报表。不能用总盘数字拆出假的渠道或游戏占比。
