# 前后端技术架构

这里是建议，不是已经开工的决定。你确认前，不把现有运营看板改成这套结构。

## 为什么不继续把计算放在现在的网页里

现在的运营看板是一个前端网站：React、TypeScript、Vite，报表在浏览器里解析，结果主要留在浏览器。它适合看已经附带的日报。

Platform Intelligence 要保存导入版本、字段模板、对账失败和分析笔记。这些如果只放在浏览器里，换电脑会丢，也不方便以后多人使用。所以新系统建议分成网页和本机数据服务。现有看板先不动。

## 建议的组合

| 部分 | 建议 | 理由 | 代价 |
| --- | --- | --- | --- |
| 网页 | React + TypeScript | 和现有看板同一语言，组件和类型清楚 | 需要单独的新目录，避免和旧看板缠在一起 |
| 界面组件 | Tailwind CSS + shadcn/ui | 浅色和深色、表格、对话框有一致规范 | 外观会和现在的自定义样式不同。这是新系统，不是改旧皮肤 |
| 图表 | Apache ECharts | 趋势、柱状和以后的贡献瀑布需要同一套交互 | 比现在手写的折线重。第一版只用到趋势和条形 |
| 服务 | Python + FastAPI | 导入、校验和指标放在一处，网页只负责展示 | 本机要同时开网页和服务 |
| 表格处理 | pandas | 读 Excel 和 CSV、预览、对账都直接 | 大文件会占内存。第一版是日报，行数很小 |
| 分析库 | DuckDB | 本机一个文件就能按平台和日期查询，以后迁到 PostgreSQL 时 SQL 大部分能留下 | 要约定谁能打开这个文件，避免复制出两份正式库 |
| 原始与标准化存档 | Parquet | 保留每次导入的列，方便重放 | 不能手改。修改必须走新的导入批次 |
| 正式库 | 第一版不用 PostgreSQL | 你现在是单机。过早上服务器没有登录场景 | 阶段 7 再迁。迁移前不要写只有 DuckDB 才有、PostgreSQL 没有的冷门语法 |

不建议第一版就上登录、云数据库或在线表格服务。那会碰到权限和公司数据出境，而阶段 7 之前没有这个必要。

Excel 读取如果继续用有已知风险的旧表格库，服务端要用当前仍在维护的读表方式，并且只接受你上传的文件，不把文件转到外部网站。具体库在编码前再定，不在规划里锁死一个有安全公告的版本。

## 请求怎么走

网页不直接改 Parquet。它只调用本机 FastAPI。

- 上传文件到预览接口，得到批次草稿和校验。
- 确认接口把草稿变成正式批次。
- 查询接口按平台、日期、币种返回指标。
- 归因接口只返回引擎算好的四层结构。

网页可以缓存一次查询，但刷新后以服务为准。演示布局用的假数据必须来自带 `demo: true` 的接口或本地夹具，不能和正式查询混用。

## 以后怎么扩展

- 新平台：加平台记录和映射模板，不复制一套页面。
- 新国家：市场字段决定时区和默认币种。
- 新报表：新的报表类型和新的事实表，不把明细行塞进平台日。
- 新角色：阶段 7 在服务上加身份。网页只根据接口返回的可见平台来画导航。
- AI：阶段 6 增加一个只读接口。模型只能收到引擎已经输出的 JSON。原始报表不作为提示词送出。若使用外部模型，要你另行授权。

## 和现有看板的关系

现有看板继续服务现在的地址和现在的附带日报。新系统的第一批真实数据，来自你再次导入或从现有 CSV 做一次有记录的导入，而不是把浏览器里的状态当成正式库。

这样两边在你确认之前互不影响。
